# Reference — Story Point table (Circle Delivery)

Vendored verbatim, and **in German on purpose**: this is the company
reference the teams estimate against, and a translation would drift from
the convention it exists to hold. Used by the dev mode (`dev.md`) for one
analogy estimate — find the nearest counterpart, name it, done. Never a
derivation, never a discussion, never an input to the plan.

- **Source:** Nuclino, Circle Delivery — "Story Point Referenztabelle"

- **As of:** 11.08.2026 (fetched 18.08.2026)
- **Maintenance:** deliberately **not** fetched at runtime — the table is
  stable by construction, and stability is its purpose. Updating it after
  a drastic change to the article is a maintainer task (decision E-0020).
  If it looks wrong for the project at hand, say so in one line and
  estimate against it anyway; do not quietly re-derive it.
- **The examples are the anchors.** Estimate against a named example
  ("ähnlich zu *Stripe-Zahlung für ein Produkt*"), not against the
  one-line summaries in the overview table.

Everything below this line is the article's content, trimmed to what the
estimate needs: the reference table plus the estimation rules. The
article's company-internal FAQ section is deliberately **not** vendored —
this file is copied into customer repos.

## Übersicht

| Story Points | Orientierung                                                                                                                           |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| 2 SP         | Triviale Änderung oder einfache Anzeige                   |
| 3 SP         | Standard-Feature nach bekanntem Muster                    |
| 5 SP         | Mehrteiliges Feature mit Zuständen und Fehlerfällen       |
| 8 SP         | Mehrere Subsysteme, Sicherheits- oder Integrationsaspekte |
| 13 SP        | Systemübergreifend, komplexe Geschäftslogik               |

## Details und Beispiele

### 2 SP – Triviale Änderung oder einfache Anzeige

Kaum eigene Logik, ein bis zwei Dateien im Kern betroffen, keine Abstimmung mit anderen Systemen nötig. Der Lösungsweg ist beim Lesen des Tickets bereits vollständig klar.

| Beispiel                                                                  | Umfang im Detail                                                                                                                                                      | Warum diese Größe                                                                                         |
| ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| **Statische Inhaltsseite** („Über uns", FAQ, Impressum)                    | Neue Route und Seite aus bestehenden Layout-Komponenten, Inhalte hartkodiert oder aus einem vorhandenen CMS-Feld, responsive Darstellung, Aufnahme in die Navigation. | Kein Backend, keine Zustände, keine Validierung – reine Komposition vorhandener Bausteine.                |
| **Neues Feld an bestehendem Model** (z. B. Telefonnummer am Nutzerprofil) | Migration, Serializer/Form-Feld, einfache Format-Validierung, Anzeige in Detail- und Bearbeitungsansicht, bestehende Tests ergänzen.                                  | Durchstich durch alle Schichten, aber jeder Schritt folgt einem etablierten Muster im Projekt.            |
| **Sortierung für eine bestehende Liste**                                  | Dropdown mit 3–4 Sortieroptionen, Query-Parameter an den bestehenden Endpunkt, `order_by` im Backend, Sortierung bleibt beim Blättern erhalten.                       | Bestehender Endpunkt und bestehende UI werden nur erweitert; kein neues Pattern, keine neuen Fehlerfälle. |

### 3 SP – Standard-Feature nach bekanntem Muster

Ein vollständiges kleines Feature: eigener Endpunkt plus UI-Anbindung, überschaubare Fehler- und Randfälle. Der Lösungsweg ist bekannt, aber es sind mehrere Teile sauber zusammenzustecken.

| Beispiel                                                        | Umfang im Detail                                                                                                                                                                                                                                                                                                                                                                           | Warum diese Größe                                                                                                            |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **CRUD für eine einfache Entität** (z. B. „Standorte verwalten") | Neues Model mit Migration, List-/Create-/Edit-/Delete-Endpunkte mit Berechtigungsprüfung, React-Liste mit Formular (Anlegen/Bearbeiten) und Löschen mit Rückfrage, Validierungsfehler am Feld anzeigen, Tests für die Endpunkte.                                                                                                                                                           | Volles Feature über alle Schichten, aber ohne Sonderlogik – jede Einzelheit ist Standard, die Menge macht den Aufwand.       |
| **Kontaktformular mit E-Mail-Versand**                          | Formular mit client- und serverseitiger Validierung, Spam-Schutz (Honeypot oder Rate-Limit), transaktionale Mail über ein Template, Erfolgs- und Fehlerzustand im UI, Eingang wird geloggt/persistiert. **Annahme:** Der Mailservice ist im Projekt bereits angebunden – muss er erst integriert werden (Provider-Setup, Domain-Verifizierung, Bounce-Handling), ist das eine Stufe höher. | Erster externer Effekt (Mail-Versand) und ein Missbrauchsszenario, das mitgedacht werden muss – mehr als reines CRUD.        |
| **CSV-Export einer Listenansicht**                              | Export-Button, Backend-Endpunkt der die aktuell gesetzten Filter übernimmt, korrektes Encoding (Umlaute, Excel-Kompatibilität), Streaming bei großen Datenmengen, fester Spaltensatz, Tests inkl. Sonderzeichen.                                                                                                                                                                           | Klar umrissen, aber mit typischen Stolperfallen (Encoding, große Datenmengen, Filter-Übernahme), die getestet werden müssen. |

### 5 SP – Mehrteiliges Feature mit Zuständen und Fehlerfällen

Mehrere Komponenten oder ein externer Dienst sind beteiligt, es gibt echte Zustandsübergänge und Fehlerpfade, die einzeln durchdacht und getestet werden müssen. Punktuell Abstimmungsbedarf.

| Beispiel                                                                                    | Umfang im Detail                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | Warum diese Größe                                                                                                                                                                                                          |
| ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Registrierung mit E-Mail-Verifizierung und Passwort-Reset**                               | Registrierungsformular mit Passwort-Policy, Double-Opt-In-Mail mit ablaufendem Token (inkl. „Token abgelaufen"-Pfad und erneutem Versand), Passwort-vergessen-Flow, Session-Handling nach Login, Rate-Limiting gegen Enumeration, Tests für alle Pfade.                                                                                                                                                                                                                                                                                    | Drei verzahnte Flows mit Sicherheitsanforderungen; die Fehler- und Randfälle (abgelaufen, doppelt geklickt, E-Mail existiert schon) sind der eigentliche Aufwand.                                                          |
| **Stripe-Zahlung für ein Produkt**                                                          | Erstmalige Stripe-Anbindung im Projekt: SDK-Integration, Checkout-Session im Backend erzeugen, Redirect zu Stripe, Webhook-Endpunkt aufsetzen und idempotent verarbeiten (doppelte Events), Bestellstatus-Modell (offen/bezahlt/fehlgeschlagen), Erfolgs- und Abbruchseite, Verhalten bei fehlgeschlagener Zahlung, Test-Modus-Setup. **Annahme:** Stripe-Account und API-Keys existieren; die technische Anbindung ist Teil des Tickets. Ist Stripe bereits angebunden und es kommt nur ein weiteres Produkt dazu, ist das eher 3 SP. | Externer Dienst mit asynchronem Rückkanal: Webhooks, Idempotenz und Statuskonsistenz erfordern sorgfältiges Design und Tests, die über den Happy Path hinausgehen.                                                         |
| **Datei-Upload mit asynchroner Verarbeitung** (z. B. Dokumente oder Bilder an einer Entität) | Drag-&-Drop-Upload mit Fortschrittsanzeige, Validierung von Dateityp und -größe (client- und serverseitig), Ablage in Objektspeicher (S3), asynchroner Verarbeitungsjob (Thumbnails/Vorschau, ggf. Virenscan), Status im UI (verarbeitet/fehlgeschlagen) mit erneutem Versuch, Löschen inkl. Aufräumen im Speicher, abgesicherte Auslieferung über signierte URLs.                                                                                                                                                                         | Asynchroner Verarbeitungsschritt bringt echte Zustände und Fehlerpfade mit (Job schlägt fehl, Nutzer lädt währenddessen neu), dazu Speicher- und Sicherheitsaspekte – deutlich mehr Randfälle als ein synchrones Formular. |

### 8 SP – Mehrere Subsysteme, Sicherheits- oder Integrationsaspekte

Mehrere Subsysteme müssen zusammenspielen, oft mit asynchroner Verarbeitung, Datenschutz-/Audit-Anforderungen oder einem externen System, dessen Verhalten man nicht vollständig kontrolliert. Deutlich erhöhter Test- und Abstimmungsaufwand.

| Beispiel                                                   | Umfang im Detail                                                                                                                                                                                                                                                                                                                                                                                                   | Warum diese Größe                                                                                                                                                                                                       |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **DSGVO-konformer Datenexport**                            | Recherche, welche Daten rechtlich in den Export gehören und was pseudonymisiert werden muss (inkl. Abstimmung mit Datenschutz-Verantwortlichen); Nutzer fordert Export an, asynchroner Job sammelt Daten aus allen relevanten Models, personenbezogene Daten Dritter werden pseudonymisiert, Ergebnis als ZIP mit Data Dictionary, Download-Link mit Ablauffrist, jeder Zugriff im Audit-Log, Statusanzeige im UI. | Querschnitt durch das gesamte Datenmodell plus rechtliche Anforderungen – die Recherche- und Abstimmungsarbeit vor der Umsetzung ist hier ein wesentlicher Teil des Aufwands, nicht nur der Code.                       |
| **Mehrstufiger Onboarding-Wizard mit Zwischenspeicherung** | Fünf Schritte mit bedingten Verzweigungen (Antwort in Schritt 2 verändert Schritt 4), serverseitige Validierung pro Schritt, Fortschritt wird persistiert und ist nach Abbruch wiederaufnehmbar, Abschluss löst Folgeprozesse aus (Willkommens-Mail, Rollenzuweisung), Zustandsmatrix wird getestet.                                                                                                               | Der Zustandsraum (Verzweigungen × Wiedereinstieg × Validierung) wächst multiplikativ – die Kombinatorik der Pfade treibt Entwicklungs- und Testaufwand, nicht ein einzelner schwieriger Teil.                           |
| **Anbindung eines externen ERP für Produktdaten-Sync**     | Täglicher und manuell auslösbarer Sync, Mapping-Schicht zwischen ERP-Format und eigenem Datenmodell, definierte Konfliktregeln (welches System gewinnt pro Feld), Retry mit Alerting bei Fehlern, Admin-Ansicht mit Sync-Status und letzten Fehlern.                                                                                                                                                               | Externes System mit eigenem Datenmodell und unklarem Fehlerverhalten: Mapping- und Konfliktentscheidungen brauchen Abstimmung, und Fehlerbehandlung muss produktionsreif sein, weil niemand den Sync manuell überwacht. |

### 13 SP – Systemübergreifend, komplexe Geschäftslogik

Das Feature zieht sich durch die gesamte Anwendung oder führt ein neues tragendes Konzept ein (Berechtigungen, Versionierung, Echtzeit). Viele bestehende Stellen sind betroffen, Migration von Bestandsdaten ist nötig, und Designentscheidungen haben langfristige Konsequenzen. Prüft, ob sich das Ticket sinnvoll schneiden lässt.

| Beispiel                                                     | Umfang im Detail                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | Warum diese Größe                                                                                                                                                                                                                                                                |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Vollständiges Rollen- und Rechtemodell (RBAC)**            | Datenmodell für Rollen und Rechte, Durchsetzung auf API- **und** UI-Ebene (Buttons/Ansichten ausblenden reicht nicht), Admin-UI zur Rollenvergabe, Migration aller Bestandsnutzer, Objekt-Berechtigungen für Sonderfälle („nur eigene Abteilung"), Tests für die Rechtematrix über alle bestehenden Endpunkte.                                                                                                                                                                                                                                                                                                                   | Querschnittsthema: Jeder bestehende Endpunkt und jede Ansicht ist betroffen, und Fehler sind Sicherheitslücken – die Breite und das Risiko bestimmen die Größe, nicht ein einzelner komplizierter Algorithmus.                                                                   |
| **Formular-Konfigurator mit gemeinsamer Auswertungstabelle** | Fachbereich baut eigene Erfassungsformulare aus Feldtypen zusammen (Text, Zahl, Datum, Auswahl, Mehrfachauswahl), inkl. Pflichtfeldern, Validierungsregeln und abhängigen Feldern (Feld B erscheint nur bei bestimmter Antwort in Feld A); Einträge aller Formulare landen in **einer** gemeinsamen Tabelle mit Sortierung und Filterung auch über die dynamischen Felder (typgerecht: Zahlenbereich, Datumsfilter, Auswahlwerte); Schema-Speicherung (z. B. JSONB) mit Umgang mit Schemaänderungen, ohne Alt-Einträge zu brechen; Rendering-Engine für die Formulare; Tests über Feldtypen × Validierung × Filterkombinationen. | Die Daten haben keine feste Form, müssen aber gemeinsam angezeigt, sortiert und gefiltert werden – das dynamische Schema zieht sich durch alle Schichten (Datenmodell, Query-Bau, UI) und macht aus jedem Standardproblem (Validierung, Filterung, Migration) ein Sonderproblem. |
| **In-App-Benachrichtigungscenter mit Echtzeit-Updates**      | WebSocket-Infrastruktur inkl. Reconnect-Handling, Notification-Center mit Lese-/Ungelesen-Status, Benachrichtigungspräferenzen pro Ereignistyp, E-Mail-Digest als Fallback für inaktive Nutzer, Erzeugung der Events an allen relevanten Stellen im Bestandscode, Lasttest der Zustellung.                                                                                                                                                                                                                                                                                                                                       | Neue Infrastruktur (Echtzeit-Kanal) plus Integration in viele bestehende Abläufe plus Fallback-Logik – drei Baustellen, die einzeln beherrschbar wären, aber zusammen ein tragendes neues Subsystem ergeben.                                                                     |

## Schätzregeln

- Der Aufwand sollte relativ zu anderen Tickets geschätzt werden. Das können andere Tickets in eurem Projekt sein, eine eigene Referenztabelle für euer Projekt, oder diese generische Referenztabelle hier.
- Aufwandtreiber sind:
  - Quantität (etwas muss sehr oft gemacht werden oder an sehr vielen Stellen)
  - Komplexität (es ist klar, was gemacht werden soll, aber es ist einfach schwierig)
  - Unsicherheit (es ist noch nicht klar, was genau gemacht werden soll oder ob es geht)
- User Stories sollten **nicht** basierend auf der Zeit geschätzt werden ("Ich brauche für den API-Endpoint vrstl. 3 Stunden"), weil man dann andere Gewerke auslässt, Abstimmungen, Abnahme, Tests etc.
- Die Schätzung sollte alle Arbeiten und Gewerke beinhalten, welche benötigt werden, um ein Ticket fertig zu machen, also Konzeption, Design, Frontend, Backend, Tests, Abnahme etc. Die Referenztickets beinhalten das aber auch. Wenn ein Gewerk deutlich umfangreicher ist, als in den Referenzen, kann das ein Treiber für eine höhere Kategorie sein.
